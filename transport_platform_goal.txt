# MASTER DEVELOPMENT PROMPT
## Production-Grade Driver & Customer Live Tracking Platform

You are acting as a **senior international mobile application architect and full-stack engineer**.

Build this application from scratch as a **production-quality commercial product**, not as a prototype or simple demo.

The product is a vehicle/driver booking and live-tracking platform with:
- Driver mobile application
- Customer mobile application
- Owner/admin dashboard
- Real-time GPS tracking
- Booking management
- Driver assignment
- Vehicle management
- Push notifications
- Google Maps
- Background location tracking
- Secure authentication
- Scalable backend

Deployable to: Google Play Store, Apple App Store, AWS production infrastructure.

Prioritize: Reliability, Security, Scalability, Performance, Clean architecture, Excellent UX, Maintainability, Production deployment readiness.

# 1. TECHNOLOGY STACK

## Mobile
React Native, TypeScript, React Navigation, Zustand or Redux Toolkit, Axios, Socket.IO Client, Google Maps, Firebase Cloud Messaging, Background GPS, Secure storage.

Support Android + iOS. One codebase. Role-based experiences:
```
LOGIN → DRIVER → Driver app
      → CUSTOMER → Customer app
```

## Backend
Node.js, TypeScript, Express.js, Socket.IO, MongoDB, Mongoose, Redis-ready, JWT + Refresh tokens, bcrypt, Zod, Helmet, CORS, Rate limiting, Pino/Winston logging.

Architecture: Routes → Controllers → Services → Repositories/Models

---

# 2. DATABASE

Use MongoDB. Use GeoJSON for locations:
```json
{ "type": "Point", "coordinates": [longitude, latitude] }
```
Coordinates are ALWAYS [longitude, latitude]. Create 2dsphere indexes.

---

# 3. LIVE LOCATION ARCHITECTURE

```
Driver Phone → GPS → React Native → Socket.IO → Node.js Server
                                              ├── Redis (live state)
                                              ├── MongoDB (persistent)
                                              └── Rooms → Customer / Owner Dashboard
```

Use WebSockets. Do NOT poll.

---

# 4. REDIS ARCHITECTURE

Keys:
```
driver:{driverId}:location
driver:{driverId}:status
driver:{driverId}:connection
booking:{bookingId}:active
```

Create a LocationStateService abstraction — can start with memory/MongoDB, upgrade to Redis later.

# 11. DRIVER LOCATION APIs

```
POST /api/drivers/location
GET  /api/drivers/:id/location
GET  /api/drivers/nearby
PUT  /api/drivers/status
```

Payload: { latitude, longitude, speed, heading, accuracy }
Validate all fields. Reject invalid GPS data.

---

# 12. SOCKET.IO

Driver: driver:connect, driver:location:update, driver:status:update
Customer: booking:join, booking:leave
Server: location:broadcast, booking:status, driver:assigned, driver:online, driver:offline

Rooms: driver:{driverId}, booking:{bookingId}, owner:live-tracking

Authenticate via JWT. Never trust client-provided driverId.

---

# 13. GPS UPDATE POLICY

Moving: every 3-5 seconds
Stationary: every 15-30 seconds
Distance filter: ~10 meters

Config: LOCATION_UPDATE_INTERVAL, LOCATION_DISTANCE_FILTER

Handle: GPS unavailable, permission denied, poor accuracy, network failure, socket disconnect/reconnect, app background/foreground, device lock.

---

# 14. BACKGROUND LOCATION

Critical production feature. Driver app must track when app minimized, phone locked, or another app open.

Android: location permissions, background location, foreground service, battery optimization
iOS: location permissions, background capability, Info.plist, native config

---

# 15. BOOKING FLOW

```
Select pickup → Select destination → Request booking → Backend assigns driver
→ Driver accepts → Customer gets driver info → Live tracking → Trip starts → Trip completes
```

Statuses: REQUESTED → ASSIGNED → DRIVER_ACCEPTED → DRIVER_ARRIVING → TRIP_STARTED → TRIP_COMPLETED
Also: DRIVER_REJECTED, CANCELLED

Use a state machine. No arbitrary status changes.
